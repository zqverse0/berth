# 项目知识库（`.berth/knowledge/`）

用户和 Agent 共用的项目教材：只写**代码里读不出来的**——为什么这样设计、核心概念、做过的决策、踩过的坑。
结构（有哪些文件、谁调用谁）现查代码，不抄进笔记。

- 全项目（含 worktree）只有一份，在主项目：路径用 `berth project . knowledge root` 取（下文 `<vault>`），不写当前 checkout 里的副本。
- 笔记由 Agent 写和维护，用户读、提意见。
- 没有 `.berth/` 时请用户在 Berth 里启用，不要自己建。只在用户要求时写；写完不提交，由用户在主项目提交 `.berth/knowledge`。

## 格式

文件名 = 标题（全库唯一，不用 `/ \ : * ? " < > |`），放在与 `type` 同名的目录：

| 目录 | 写什么 | 正文骨架 | 新建状态 |
|---|---|---|---|
| `地图/` | 导航与学习路径；`地图/首页.md` 是面板首页，链接所有地图和主要模块 | 自由 | 已确认 |
| `概念/` | 一个核心名词一篇 | 是什么 / 为什么存在 / 在哪出现 | 已确认 |
| `模块/` | 一个模块一篇 | 职责 / 为什么这样设计 / 入口 / 和谁交互 | 已确认 |
| `决策/` | 用户拍板的方案、原则与取舍 | 背景 / 决定 / 放弃的方案 | 草稿 |
| `经验/` | 查清根因的问题 | 症状 / 根因 / 正确做法 | 已确认 |

```yaml
---
type: 模块                      # 必填，上表之一
verified_at: <git sha>          # 必填：最后对照代码核实时的 `git rev-parse --short HEAD`
code: [src-tauri/terminal/]     # 模块、经验必填；仓库相对路径，目录以 / 结尾
status: 草稿                    # 可选：草稿 | 已确认（缺省）| 已取代
aliases: [termd]                # 可选：双链也按别名解析
supersedes: ["[[旧标题]]"]      # 取代旧笔记时填，旧笔记改 status: 已取代，不删
sources: [claude:<sessionId>]   # 可选：依据的会话
---
```

`code` 下的文件在 `verified_at` 之后有提交即「可能过期」。未知字段原样保留。
`来源/` 由 Berth「发现」页维护（`kind`、`url` 必填，同一 `url` 只能一篇），读过后在正文写 `## 摘要` 并改 `digested: true`。

## 写作纪律

- 先查重（`berth project . knowledge search <标题>`），有就更新。每篇至少一个 `[[双链]]`，新建后回到相关笔记补上指向它的链接。
- 一篇讲一件事，15–40 行；先讲是什么、为什么，再讲在哪、和谁交互；入口只列第一个该打开的文件，不复述代码。
- 断言必须对照当前代码核实（读过源码才算），核实不了的不写；文档与代码不一致按代码写并在总结里列出。
- 第一次出现的项目术语链接到它的概念笔记。不写密钥与隐私，不照抄 `AGENTS.md`。

## 维护

**更新知识库**（用户说「更新 / 整理知识库」，或记忆面板「交给 Agent」发来的请求）：先看现状再决定做什么，可重复执行。

1. 空库或缺模块 → 写第一批笔记：读 `AGENTS.md`、`README`、架构文档；找入口与依赖核心（有 codegraph 等代码索引就用，没有就读代码），
   按依赖关系划出顶层模块。**先把提纲（首页 + 模块 + 至少 10 个概念）给用户确认**，再按 模块 → 概念 → 首页 的顺序写。
   代码很少的新项目：只写首页（目标、边界）和已做的决策。
2. 有新会话 → 吸收：`berth project . knowledge digest > /tmp/digest.md`（按 `<vault>/.curation.json` 的 `since` 增量；
   `truncated: true` 时用 `--since <next_since>` 续读）。只留下次还用得上的：拍板的方案与取舍 → `决策/`，查清的问题 → `经验/`，
   对模块的新认识 → 更新 `模块/`；丢弃寒暄、进度、没采纳的提议。全部写完再写游标 `{"since": "<next_since>"}`。
   用户以后都要遵守的要求不写这里：告诉用户，放专家提示词（跨项目）或项目 `AGENTS.md`（项目级）。
3. 体检：`berth project . knowledge lint`，ERROR 修完，WARN 逐条判断；「可能过期」的对照代码改正文并更新 `verified_at`。
   再人工看：结论矛盾却没 `supersedes`、有模块没笔记、首页没链接到的模块。
4. 总结：新增 / 更新 / 取代的笔记，待用户确认的草稿，拿不准的点，建议从哪篇开始读。

**待入库**（`<vault>/待入库/`）：任务、想法归档时自动进来，一条一个文件，不算笔记。平时不自动处理，也不主动催用户；归档结果里的 `inbox` 只是当前总数。
用户说要维护知识库时，放在上面第 1 步之前处理：

1. `berth project . knowledge inbox ls`，先报数量。
2. 逐条读文件（任务还可以看里面的提交、偏离记录，关联会话用 `session show` 读），给建议：写进哪篇笔记、写什么，或者不入库及理由。
3. 用户确认后才写笔记，然后 `berth project . knowledge inbox done <来源> --outcome <结果>`（如 `写入 [[标题]]`、`不入库：<理由>`），文件移到 `待入库/已处理/`。用户没确认的留着，下次再说。

**记一笔**（用户说「记到知识库」）：判断类型 → 查重 → 新建或更新 → 补链接。

**查询**（只读，需要时用）：按路径 `berth project . knowledge for <路径>`；按主题 `berth project . knowledge search <词>`（`--type` 只看一类）；
`berth project . knowledge show <标题>` 读全文与链接。只信 `已确认`，`草稿` 未确认，`已取代` 已作废。

**整理指定会话**（用户点名某几个会话）：`berth project . session list`（`--agent` / `--group` 筛选）找到会话，
`berth project . session show <id> --agent <tool id>` 读全文（长会话先 `--tail 20`，再 `--grep <词>`）；
按「吸收」的取舍写入，`sources` 加上 `<tool id>:<id>`，不动游标。
